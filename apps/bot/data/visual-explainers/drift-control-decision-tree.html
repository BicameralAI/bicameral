1. Reduce drift by classifying the problem first

Pick the drift family, then choose the matching controls.

1.1 Application drift

Make every runtime boundary explicit.

Inventory cross-boundary communication and attach each boundary to a contract family, source of truth, and mismatch flow.

  • Create a written inventory covering cloud, bot, MCP, and integrations.
  • Label each boundary as semantic contract, API contract, or deployable artifact.
  • Document where the single source of truth lives.
  • Define a version synchronization flow for developers and users when versions mismatch.
  • Add explicit version control for the ingestion envelope.
  • Add a documented mismatch/update flow for ingestion-envelope changes.
  • Confirm the hosted UI / local daemon setup keeps the UI in the bot repo and auto-generates a PR to the hosted repo on frontend updates.
1.2 Developmental drift

Gate implementation changes deterministically.

Shift from implicit trust in branch activity to traceable gates, provenance, and validation against feature claims.

  • Put governance checks in place at PR / commit stages.
  • Ensure change tracking includes a ledger / provenance trail for implementation updates.
  • Add substantiation / validation so a feature is checked against what it claims to do.
  • Define local-machine provenance expectations for commits / PRs.
  • Confirm deterministic governance work is centered in factory as the hub repo.
1.3 Ticket / decision drift

Make decision visibility reliable across collaborators.

Ticket handling becomes a deterministic workflow, while reusable automation graduates into factory.

  • Define a deterministic ticket-management workflow so tickets are reliably seen across collaborators.
  • Move generally useful workflow automation into factory when it is reusable by the team.
  • Share reusable ticket-detection / workflow automation in the dev environment channel after pushing it to factory.
2. Apply the new conceptual model

Prefer one governed source and only the duplication that earns its keep.

Repo shape

Delete or fold back duplicate pathways.

  • Delete the sidecar repo if no work needs to be preserved.
  • Delete the SDK repo if it is not being actively pursued as a separate repo.
  • If SDK-like functionality is still needed, keep it inside the integrations layer rather than as a separate repo.
  • Verify bicameral cloud is explicitly included inside the governed control-plane model.
Operating principle

Single source of truth + deterministic synchronization.

Prefer governed sources, explicit version flows, and reproducible updates over duplicate repos or duplicate pathways. Add a separate repo only when the boundary has a strong reason to exist independently.

3. Use factory as the control hub

Other repos should relate back to factory rather than inventing parallel control planes.

Control hub

Factory owns deterministic governance language and reusable workflow.

  • Confirm bicameral factory is the designated single source of truth repo.
  • Document how other repos relate back to factory as the hub.
  • Update governance documentation to reflect cloud as part of the governed product/control plane.
4. Prioritize control-plane work around security and SOC 2

SOC 2 document readiness becomes the highest-priority control-plane thread.

Security priority

Translate governance work into evidence, ownership, and document posting.

  • Treat SOC 2 integration as the top priority within the control-plane work.
  • Incorporate security-related items like SBOM into the control-plane scope.
  • Review the governance / control-plane writeup already sent earlier.
  • Use the exported SOC 2 document requirements CSV and filter by category.
  • Add or complete mappings from required documents to templates / instructions in the repo.
  • Use the Vanta MCP to accelerate document posting / management.
  • Identify which document categories require Jin's ownership vs Kevin's ownership.
