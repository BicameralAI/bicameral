# Runtime Protocol Contracts

This document contains stable machine contracts used by local surfaces and
clients to request, report, or render Bicameral lifecycle state.

Use this file for protocol, command, capability, trace, and staged-response
vocabulary that is stable enough for clients to depend on but is not the core
decision lifecycle itself.

## Promotion Rule

Promote a term here when changing it would affect compatibility between the
daemon and a surface such as MCP, CLI, dashboard, TUI, integrations, or cloud
clients.

Do not promote local helper classes, private component state, or implementation
function names unless a protocol or conformance fixture makes the semantics
durable.

## Contracts

`ToolRequest`
: Action contract for local tool surfaces such as MCP, CLI, dashboard, or TUI.

`Authenticated remote review action`
: Verified user action initiated from an external review surface, such as a
  Slack modal, Linear action, or hosted review UI. It is not source ingest,
  local `ToolRequest`, or egress; it may request governed review only after the
  bot verifies the callback, binds the external identity to a Bicameral actor,
  and accepts the action through policy.

`Hosted bridge route family`
: Paired browser-origin route family on the bot gateway for user-level hosted web
  access to local Bicameral. It is not `ToolRequest`, not
  `ExternalIngestEnvelope`, and not a separate authority surface. Bridge routes
  add origin/CORS validation, CSRF/replay protection, pairing lifecycle with
  expiry/revocation, and capability handshake scoped to hosted bridge support.
  Pairing is user/operator-level; project selection and workspace binding happen
  through narrower flows after pairing. See
  `docs/specs/hosted-bridge-user-level-pairing.md`.

`Hosted pairing code`
: Short-lived, human-entered locator generated by the local daemon for one
  transient hosted-bridge pending request. The initiating browser displays it;
  a local terminal accepts it and reveals the matched origin/account before a
  separate explicit decision. The daemon retains only a digest. Possession,
  lookup, or entry is not approval, a bridge session, local actor authority,
  Product membership, workspace binding, or canonical state.

`ToolResponse`
: Daemon response to a ToolRequest. It carries command status, payload, typed
  unsupported/deferred results, and traceable request context without making the
  calling surface authoritative.

`ToolRequest Dispatcher`
: Bot-owned runtime path that validates local ToolRequest authority, routes
  supported commands, and returns ToolResponse outcomes. Local surfaces may call
  it; they must not bypass it with surface-owned canonical event writes.

`CapabilityReport`
: Daemon capability handshake response that tells local surfaces which
  ToolRequest protocol version and command capabilities the running daemon
  supports. Includes per-feature alpha capability advertising (lookup,
  request_correction) with support status, version-gating, and
  deprecation/migration metadata. It is compatibility evidence for startup and
  command availability, not governance authority.

`AlphaCapabilities`
: Structured per-feature capability metadata within CapabilityReport. Each entry
  advertises whether a feature (e.g. lookup, request_correction) is supported,
  deferred, or unsupported, plus the minimum daemon protocol version and
  deprecation/migration posture. Surfaces must not enable lookup or correction
  behavior unless the daemon explicitly reports support. This is compatibility
  metadata, not governance authority.

`FeatureSupportStatus`
: Per-feature support classification: supported (active), deferred (recognized
  but intentionally delayed), or unsupported (not available in this version).
  Surfaces render this directly — they must not derive their own classification.

`MigrationStatus`
: Deprecation/migration posture for a capability: current (stable), deprecated
  (works but a newer path exists), or migrating (callers should check the
  migration target). Surfaces should render warnings for deprecated features.

`PROTOCOL_VERSION`
: Local ToolRequest wire compatibility version used by MCP and other surfaces to
  decide whether they can speak to the running daemon. A mismatch is a
  compatibility failure and should not be recovered by falling back to legacy MCP
  authority.

`StagedPreflightResponse`
: Typed response envelope for preflight-related requests. It lets clients render
  daemon-owned stage state without guessing whether capture, projection, lookup,
  enforcement, or session directive behavior is configured, unavailable,
  successful, or advisory.

`PreflightStageCapability`
: CapabilityReport entry advertising which preflight stages the daemon can
  report and what alpha cut-line behavior a client should expect.

`RuntimeTrace`
: Operational receipt struct for Bot-MCP command correlation. Carries
  request_id, command, caller_surface, actor_id, workspace_id, session_id,
  provider, model, task_kind, token_usage, latency_ms, status, and
  failure_reason. It is not governance authority.

`TraceStatus`
: Trace-scoped status enum mirroring ToolResponseStatus for runtime trace
  context.

`TokenUsage`
: Reasoning provider token metadata carried within a RuntimeTrace.

`DispatchOutcome`
: Typed dispatch result wrapper used by dispatch-with-trace paths to pair a
  ToolResponse with its RuntimeTrace.

`GraphSnapshotService`
: Bot-owned runtime boundary for graph snapshot resolution, graph readiness,
  file/range inspection, symbol resolution, refresh, and currentness
  evaluation. It may return derived graph facts and typed readiness; it must not
  append governance events, accept BindingEvidence, or decide compliance.

`CodeLocator`
: Deterministic runtime service that uses available graph/source context to
  locate candidate code targets. It returns advisory or verified locator
  results, but it does not materialize BindingEvidence or compliance outcomes.

`LocatorResult`
: Response contract for `code.locate`. It carries candidate code targets,
  readiness, evidence-state caveats, reasons, warnings, and next actions. A
  LocatorResult is discovery evidence only; only a governed binding path can
  accept BindingEvidence.

`GraphStatusResult`
: Response contract for graph readiness/status queries. It reports the daemon's
  current graph capability and snapshot/scope state without claiming global
  repository coverage or implementation safety.

`GraphRefreshResult`
: Response contract for explicit graph refresh requests. It reports refresh,
  snapshot, slice, job, warning, and next-action state without mutating
  accepted Decision, signoff, compliance, or binding authority.

`PreflightLocatorContext`
: Optional enrichment on preflight responses that carries CodeLocator candidates
  and graph-readiness caveats. It is advisory context for callers, not a
  compliance, safety, no-conflict, or blocking result.

`SearchCodeContext`
: Optional enrichment on search responses that carries locator candidates and
  code-readiness caveats. It helps users find code-adjacent context without
  making search results governance facts.

`FindCodeImpactResult`
: Response contract for `decision.find_code_impact`. It summarizes planned
  discovery over an accepted Decision, candidate code-impact targets, caveats,
  and next actions. It may recommend explicit binding.create follow-up for
  verified candidates, but it never creates BindingEvidence directly.

`CodeImpactCandidate`
: Discovery-only candidate inside FindCodeImpactResult. It is distinct from
  BindingEvidence and remains non-authoritative until the explicit binding path
  revalidates and accepts it.

`AlphaProjectionOutcome`
: Typed result of an alpha candidate-projection attempt over observed evidence.
  It reports whether projection produced candidates, found no decision-like
  claim, was deferred for a provider-side reason, or was hard-rejected by
  validation/policy. Projected candidates still require review; this outcome is
  not compliance, signoff, source approval, enforcement, or Decision Ledger
  authority.

`ProjectionDeferralReason`
: Typed provider-side reason a projection was deferred — provider config
  missing, config invalid, provider unavailable, timeout, or invalid provider
  output. It guides the operator toward the correct repair action and carries no
  secret material or governance authority.

`ProjectionProviderReadiness`
: Non-secret projection-provider setup state (ready flag, configured mode, and
  status summary) surfaced through CapabilityReport and runtime responses so
  callers can tell whether candidate projection is available before attempting
  it. It must never expose API keys, tokens, or secret material, and it is
  protocol/read-model state, not compliance or signoff authority.

`ProjectionProviderMode`
: Configured alpha projection provider mode — local CLI (alpha default), local
  OpenAI-compatible endpoint, or hosted Bicameral service. It is
  provider-selection metadata reported alongside readiness, not reasoning
  authority or governance state.

`EnvelopeBridgeOutput`
: Runtime bridge result that converts a `ProviderItemEnvelope` provider fact
  into bot-owned `Source` and `SourceSnapshot` capture state. It models the
  first canonical provider-to-bot capture step; it does not create
  DecisionCandidate or Decision objects, emit review/signoff/compliance
  commands, write the event store, accept SourceBinding, or make live provider
  calls.

`ReasoningProjectionService`
: Daemon-owned service that routes a ProjectionRequest through the configured
  ProjectionProvider and returns a typed ProjectionResult. It is the alpha
  projection gate enforcing that DecisionCandidate creation requires daemon-owned
  projection, and it never manufactures generic fallback candidates. It is not
  compliance, signoff, source-approval, enforcement, merge-safety, or Decision
  Ledger authority.

`ProjectionProvider`
: Provider trait/role the ReasoningProjectionService calls to project candidates
  from evidence plus advisory inputs. It defines the swappable projection
  boundary (project plus mode) for reasoning backends; implementing it does not
  grant compliance, signoff, source-approval, enforcement, or merge-safety
  authority.

`ProjectionRequest`
: Wire input to projection — source identity and type, optional title,
  description, and snapshot content, evidence excerpts, and advisory candidate
  hints and drafts. It is a transport contract carrying advisory inputs only; it
  is not compliance, signoff, source-approval, enforcement, or merge-safety
  authority.

`ProjectionResult`
: Wire output of projection — an AlphaProjectionOutcome, any
  ProjectedCandidateProposal items, the ReasoningMode used, optional detail, and
  a projection id. It reports what projection produced for review; it is not
  compliance, signoff, source-approval, enforcement, merge-safety, or Decision
  Ledger authority.

`ReasoningMode`
: Provider mode selected for a projection — local CLI (alpha default), local
  OpenAI-compatible endpoint, hosted Bicameral service, or deterministic
  (test/tracer) provider. It is provider-selection metadata reported on
  ProjectionResult and is the runtime-side companion to ProjectionProviderMode
  readiness; it is not reasoning authority, governance state, or
  compliance/signoff/source-approval/enforcement/merge-safety authority.

## Command Vocabulary

`ingest.submit_local`
: Local ToolRequest command for submitting local evidence or candidate drafts
  into daemon governance.

`preflight.run`
: Read-only advisory constraint lookup command. It may retrieve relevant
  Decisions, candidates, source links, graph snapshot scope, readiness, and
  warnings. It must not mutate Decisions, candidates, signoffs, compliance, or
  bindings.

`code.locate`
: Read-only ToolRequest command for deterministic code target discovery. It
  returns LocatorResult and must not write governance state.

`graph.status`
: Read-only ToolRequest command for graph readiness/status. It returns
  GraphStatusResult and must not index or mutate graph cache as a side effect.

`graph.refresh`
: Explicit ToolRequest command for bounded graph refresh. It returns
  GraphRefreshResult and may update graph cache/job state, but not governance
  state.

`decision.find_code_impact`
: Read-only planned discovery command for finding code targets likely relevant
  to an accepted Decision. It may aggregate multiple code.locate calls and
  return FindCodeImpactResult; it must not create BindingEvidence.

`history.list`
: Query command for derived history views. It reads projection state and is not
  event authority.

`search.query`
: Query command for derived search views. Search results are not governance
  facts.

## Component Vocabulary

The following may be documented under the parent protocol term but should not be
promoted as standalone domain entities unless they become independent contracts:

- preflight stage status enums such as capture, projection, lookup,
  enforcement, and session directive modes;
- graph and locator helper enums such as `LocatorEvidenceState`,
  `FindCodeImpactStatus`, `GraphJobState`, `SliceCompleteness`,
  `ScopeProofState`, `AllowIndex`, and `RefreshTrigger` unless a client must
  depend on them outside their parent response;
- helper structs such as `FindCodeImpactHint`, `FindCodeImpactNextAction`,
  `SearchPlanSummary`, and caveat detail records unless they gain independent
  protocol meaning;
- projection provider implementations such as `DeterministicProjectionProvider`
  (alpha tracer/test provider) and `UnavailableProjectionProvider`, which realize
  the `ProjectionProvider` trait but carry no independent contract or governance
  authority;
- advisory projection input helpers such as `CandidateHintInput` and
  `CandidateDraftInput` carried inside a `ProjectionRequest`;
- implementation constants such as `SUPPORTED_COMMANDS` and
  `DEFERRED_COMMANDS`;
- helper functions such as `dispatch()`;
- dashboard-local error classes such as `DeferredCommandError`.

## Boundaries

- Protocol compatibility is not product acceptance.
- Capability support is not governance authority.
- Runtime traces and operational receipts may support debugging and audit, but
  they do not affect governance, signoff, compliance, or Decision state.
- Unsupported and deferred commands should stay explicit typed outcomes; clients
  must not fall back to legacy local authority.
- Source-adapter ingest, authenticated remote review actions, hosted bridge
  routes, local `ToolRequest`s, and future `Egress` use separate contracts even
  when they all route through bot-owned authorization policy.
- Hosted bridge pairing is not project membership, project selection, workspace
  binding, source authority, signoff, or event-store authority.
