# Open PR triage for BicameralAI/bicameral

Kevin (decision owner) asks for this to decide quickly what needs him and to get
every open PR moving. The bot's daily post only counts non-draft PRs as
approved/unapproved; your job is to say, per PR, what the next step is and who owns it.
Every claim must be something you checked on GitHub during this run.

## Governance (apply to every judgment)

- Code owners: **Knapp-Kevin** (Kevin Knapp, also decision owner), **jinhongkuan**
  (Jin Kuan), **silongtan** (Silong Tan). All three own the repo by default.
- Only Knapp-Kevin and jinhongkuan own `.github/`, `docs/architecture/`,
  `governance/`, `tools/governance/` and the root governance files (GOVERNANCE.md,
  MAINTAINERS.md, SECURITY.md, LICENSE, NOTICE). Re-read `.github/CODEOWNERS` each run
  in case it changed (it is generated by `tools/governance/check.py`).
- Changes under `.github/` need Kevin's decision-owner sign-off, whoever else approved.
- The last pusher to a PR's head cannot approve their own head. If Jin authored or last
  pushed a PR touching a Jin+Kevin-only path, Kevin is the only possible approver, and
  vice versa (a deadlock if Kevin pushed last and Jin is the author: say so).
- An approval counts only for the head SHA it was given on. A push after an approval
  makes it stale; report it as stale, not approved.
- An approval scoped to a specific head or stack does not authorize merging anything else.
- This skill never approves, requests changes, or merges. It reports, and on request
  comments, opens draft fixups, and sets assignees/reviewers.
- PRs Jin already approved as code owner (on the current head) are left out of
  "waiting on Kevin" items and out of those counts.

## Step 1: Gather state (read-only)

1. List **all** open PRs, drafts included (the bot excludes drafts; say how many drafts
   you added). Note base branch: a PR targeting another PR's branch is stacked, not
   headed to `main`.
2. For each PR, check on its github.com page (Conversation, Commits, Checks, Files):
   - head SHA, author, and who pushed the latest commit;
   - each review: reviewer, state, and the commit it was given on (stale or current);
   - requested reviewers and how long they have been idle;
   - CI checks on the head (green / failing / running; required vs not);
   - mergeability (clean / conflicts / blocked) and unresolved review threads,
     including bot reviewers such as CodeRabbit;
   - changed paths, mapped to CODEOWNERS (flag `.github/` and Jin+Kevin-only paths);
   - last activity date.
3. For unapproved PRs whose risk is not obvious, read the diff and look for concrete
   problems (dropped or `#[ignore]`d regression tests, error paths that change what
   another component reports, version-skew failures). Cite file:line.
4. If something can't be checked (e.g. you can't compile two PRs together or run the
   Rust/dashboard tests), say so in one line rather than implying it was.

Never infer state from branch names, titles or the bot's numbers. If the bot's count
disagrees with what you found, trust GitHub and mention the difference.

## Step 2: Report

Lead with what needs Kevin. Keep it short: one bullet or table row per PR, one line
each where possible. Link every PR as `[#N](https://github.com/BicameralAI/bicameral/pull/N)`
(in Slack, `<url|#N>`). Make every count by enumerating the items first and counting
the list; never write a number you didn't count.

Open with one or two sentences: total open (with drafts), how many to merge, how many
waiting on Kevin, CI/conflict headline.

**Default grouping** (for "review the current state" style requests):

- *Ready*: approved by a code owner on the current head, green, clean. Name the
  approvers and the base branch (merge stacked children into their parent first).
- *Waiting on Kevin*: needs his approval, decision-owner sign-off, or architecture
  decision. Exclude PRs Jin already approved on the current head.
- *Waiting on others*: name the person (GitHub login) and the action.
- *Needs a decision*: a design trade-off someone must accept; state it in one line.
- *Blocked / on hold*: what it waits on (another PR, changes requested, conflicts).

**Action/priority mode** (when asked to categorize by action and priority): one table,
sorted by priority, columns `PR | Action | Pri | Signal`.
- Action: *Merge* (ready), *Remediation* (changes requested or review findings
  outstanding), *Assignment* (no owner moving it: idle reviewers, stale, needs closing),
  *Work* (author or reviewer has the next step; drafts count here).
- P0 = broken main, security, or blocking a release; P1 = unblocks other PRs or is ready
  now; P2 = active but not blocking; P3 = idle drafts and stale items. Say if none are P0.
- Put 3-4 "look at first" bullets above the table.

End with one offer of the useful next step (e.g. "Want me to post the #91 and #75
findings as review comments?"), not a list of options.

## Step 3: Follow-ups (only when Kevin asks)

Do only what was asked, and report each result with links.

**Post findings as review comments.** Submit a plain *comment* review (never approve or
request changes). Re-check line numbers against the current head before anchoring
inline comments, and say if a line moved. Put anything that has no stable line in the
review body. Reply with a link to each review (`.../pull/N#pullrequestreview-ID`) and
anything you could not confirm.

**Execute known remediations.** Open a *draft* fixup PR targeting the PR's own branch;
don't push to someone else's branch. Run the relevant tests and report counts. If
GitHub refuses a push (e.g. workflow files need a permission the app lacks), attach the
change as a `git am` patch and name who must push it. DCO sign-offs and dismissing bot
findings are human steps: list them, don't fake them. Leave maintainer decisions
(architecture, dependency pinning choices) as decisions, stated in one line each.

**Assign and delegate.** Set assignees and reviewers by who owns the paths and who has
context (authors own their drafts). Then, if asked to organize in the thread, post every
open item grouped by the person who owns the next step, Kevin first, each person tagged
with their Slack mention and GitHub login. Resolve Slack users by lookup, never by
guessing, and ask to be told if a mapping is wrong. Confirm GitHub assignees match the
list before saying they do.

## Rules of thumb

- Re-verify before every follow-up message; state may have changed since the report.
- Prefer the explicit person over "code owners" when only one person can act.
- No personal details beyond roles; no speculation about why someone is idle.
